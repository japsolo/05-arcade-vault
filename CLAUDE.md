# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

Arcade Vault: an online platform to play games and compete for the highest score. The project follows Spec-Driven Development (`/spec` and `/spec-impl`), using the skills from `Klerith/fernando-skills` (`npx skills@latest add Klerith/fernando-skills`). SPEC 01 (`specs/01-mvp-pantallas-visuales.md`) implements the visual MVP: all five screens with mock data and no real games. `references/` holds the original prototype (React + Babel, ignored by ESLint); it is the visual source of truth. `references/started-games/` holds the original vanilla canvas games that later specs port (SPEC 05 ported `02-asteroids`). SPEC 06 moved the game catalog and the scores to Supabase.

## Architecture notes

- App Router only (`app/`); path alias `@/*` maps to the repo root.
- `next.config.ts` enables `cacheComponents`, `partialPrefetching` and `experimental.agentFeedback`. `cacheComponents` changes caching/dynamic-rendering semantics, so check the docs before using data fetching or dynamic APIs.
- Tailwind v4 is wired through a Turbopack rule (`@tailwindcss/turbopack` loader for `*.css`) rather than PostCSS. Theme tokens live in `app/globals.css` (`@theme inline`, light/dark via `prefers-color-scheme`).
- Routes: `/` (home/landing), `/biblioteca` (library), `/juegos/[id]` (detail), `/juegos/[id]/jugar` (real game if registered, else simulated player), `/acceso` (auth), `/salon` (hall of fame), `/acerca-de` (about + contact form). UI is Spanish.
- The home (`app/page.tsx`) is a server component built from `components/home/*`; only `Reveal` (IntersectionObserver adds `.in` to `.reveal` sections) and `home-ctas.tsx` (session-dependent CTAs) are client components.
- The About page (`app/acerca-de/page.tsx`) is a server component that reuses `Reveal` from the home; its only client component is `components/about/contact-form.tsx`. The form posts to the Server Action `sendContact` (`app/acerca-de/actions.ts`) via `useActionState`, which sends one email to the team with the `resend` SDK. Validation, limits, the `ContactState` type and the escaped HTML/text email template live in `lib/contact.ts` (shared by client and server, no secrets). The form uses uncontrolled inputs: React 19 resets the form after each action, so on error the values come back in `state.values` as `defaultValue`. A hidden `website` field is a honeypot (filled → reports success without sending).
- Server-only env vars (in `.env`, git-ignored; keys listed in the committed `.env.template`): `RESEND_API_KEY` and `CONTACT_TO_EMAIL`. Mail is sent from `onboarding@resend.dev`, which Resend only delivers to the Resend account owner's address, so `CONTACT_TO_EMAIL` must be that address. Never expose them with `NEXT_PUBLIC_`; read them only inside the Server Action.
- Supabase connection (SPEC 04, `@supabase/ssr`): `lib/supabase/server.ts` (`await createClient()` over `cookies()`, for Server Components/Actions/Route Handlers; create one per request), `lib/supabase/client.ts` (`createClient()` for `"use client"` components) and `lib/supabase/proxy.ts` (`updateSession`, called from the root `proxy.ts` — Next 16's replacement for `middleware.ts` — to refresh the session cookie; its `matcher` skips static assets and images). `lib/supabase/public.ts` (`createPublicClient()`, plain `supabase-js` with the publishable key, no cookies or session) is for cached reads: anything inside `'use cache'` must use it, since `cookies()` is not allowed there. Never import `server.ts` or `proxy.ts` from client components. All clients are typed with `Database` from `lib/supabase/database.types.ts`, generated with the Supabase MCP (`generate_typescript_types`); regenerate it after each migration. There is no auth yet. Env vars `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (`sb_publishable_…`, public by design; data security will come from RLS). Never add a secret/`service_role` key. `scripts/supabase-check.mjs` (`npm run supabase:check`) verifies them.
- Playable games (SPEC 05): `/juegos/[id]/jugar` mounts `PLAYABLE[id] ?? GamePlayer` from `components/games/registry.ts` (`id → ComponentType<{ game }>`); only `rocas` is registered, the other games keep the simulated `GamePlayer`. Each game is a framework-free canvas engine plus a client component that mounts it:
  - Engine `lib/asteroids/` (no React, no `"use client"`): `entities.ts` is a faithful TypeScript port of `references/started-games/02-asteroids/game.js` (same constants and classes; `draw(ctx)` and `Ship.update(dt, keys)` take the context/keys instead of globals); `engine.ts` exports `createAsteroids(canvas, { onPauseChange, onGameOver })` → `{ togglePause, restart, destroy }`. Phases `ready` (waits for SPACE) / `playing` / `dead` / `gameover`, plus `paused`; HUD and overlays are drawn on the canvas. World is 800×600, canvas buffer `800·dpr × 600·dpr` with `setTransform(dpr…)`, CSS stretches it over the 4:3 `.crt-screen`. Input listens on `window`, ignores keys while focus is in `input`/`textarea`/`contenteditable`, and `preventDefault`s arrows/SPACE except in `gameover` (so SPACE can press the modal's buttons). `blur`/hidden tab clears keys and pauses. `onGameOver(score)` fires once, 1.5 s after GAME OVER; SPACE does not restart.
  - Player `components/games/asteroids-player.tsx`: creates the engine in `useEffect` and destroys it in the cleanup (callbacks via a ref, so the engine is created once per mount). With `cacheComponents`, navigating away hides the route with `<Activity>` instead of unmounting it: effect cleanups run but React state survives, so that cleanup also resets `paused` and closes the modal; coming back builds a fresh engine in `ready`. Its bar only has the player name and PAUSA/REANUDAR + SALIR (score/lives/level live in the canvas); below the CRT, `.controls-hint`; `.touch-warning` shows only with `@media (pointer: coarse)`.
  - `components/game-over-modal.tsx` (FIN DEL JUEGO: initials, GUARDAR, JUGAR DE NUEVO / VOLVER AL VAULT) is shared by `GamePlayer` and the Asteroids player; it owns the edited name and the save state. With `playable={false}` (simulated games) it shows "PARTIDA DE DEMOSTRACIÓN · NO SE GUARDA" and no input. Otherwise the name goes through `sanitizeName` and is saved with the Server Action `submitScore`.
- Catalog and leaderboard (SPEC 06), in Supabase:
  - Migrations live in `supabase/migrations/` (file name = the version `apply_migration` records) and are applied with the Supabase MCP; there is no Supabase CLI. Tables: `games` (catalog, `playable`, `sort_order`) and `scores` (`game_id`, `name`, `score`, `created_at`). Views (`security_invoker`): `leaderboard` (best score per name and game, ties go to the oldest, with `rank`) and `game_stats` (`best`, `plays`).
  - RLS: public `SELECT` on both tables; `INSERT` on `scores` for `anon`/`authenticated` only if `name ~ '^[A-Z0-9_]{1,10}$'`, `score` is 1..9,999,999 and the game is `playable` (the same rules are `CHECK`s). No `UPDATE`/`DELETE` policies, and those grants plus writes on `games` are revoked. Without auth anyone can still insert a fake score; accepted until the auth spec.
  - Reads: `getGames()`/`getGame(id)` in `lib/games.ts` (with `best`/`plays` from `game_stats`) and `getLeaderboard`, `getAllLeaderboards`, `getRecentScores`, `getTopToday` in `lib/scores.ts`. They are `'use cache'` with `cacheTag("games", "scores")` / `cacheTag("scores")`; leaderboards and catalog use `cacheLife("hours")`, home activity `cacheLife("minutes")` (its "hace X min" text and the 24 h top are computed when the cache entry is built). Client components must import only types from these modules (data comes in as props, e.g. `LibraryBrowser`, `HallOfFame`); importing a value pulls `'use cache'` into the client bundle and breaks the build.
  - Write: `submitScore` (`app/juegos/[id]/jugar/actions.ts`) validates with `lib/score-rules.ts` (`NAME_RE`, `SCORE_MAX`, `sanitizeName`, `validateScore`, shared with the client), checks the game is `playable`, inserts with the cookie server client and calls `updateTag("scores")` so the player sees the score on the next navigation. Rows inserted by hand (SQL) don't invalidate the cache; in `next dev` a request with `Cache-Control: no-cache` bypasses it.
  - Making a game playable takes both: registering it in `PLAYABLE` and a migration setting `games.playable = true`. Otherwise it plays but cannot save.
- `lib/home.ts` holds the static home copy (features, stats, pricing, FAQ). Components are in `components/`; styles reuse the classes in `app/globals.css` rather than Tailwind utilities.
- Session is simulated: `lib/session.ts` + the `useSession` hook (`lib/use-session.ts`) read `localStorage` (`av_user`) through `useSyncExternalStore`. There is no context provider: each component must call the hook itself so it hydrates with the server snapshot (`null`) even inside `Suspense` (a context made `Nav` hydrate with the user and mismatch). Don't use `useEffect` + `setState` for this (the `react-hooks/set-state-in-effect` lint rule rejects it).
- Pages that read `params` do it inside `<Suspense>` (see `app/juegos/[id]/page.tsx`) to keep the App Shell shared; `Nav` is also wrapped in `Suspense` because `usePathname` can suspend with `cacheComponents`.
- `app/layout.tsx` types its props with the global `LayoutProps<"/">` helper (generated route types), not a hand-written props type.
